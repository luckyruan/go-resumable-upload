# 项目设计：大文件上传的正确性比页面数量更重要

> 验证状态更新（2026-10-04）：11 个顶层单元测试、vet/build 通过，真实 SQL/跨资源行为和部署未验证，见 [完善记录](06-完善记录与验收.md)。下面的设计不能当作线上运行证据。

## 一、场景与学习价值

网盘、视频管理、模型训练数据平台都会遇到大文件上传。一次性 POST 的缺点是失败后通常重传全部内容。分片上传把整个文件分成连续字节区间，使客户端能够只重传失败分片。本项目训练的是后端处理数据流与状态的能力，而不是简单的 CRUD。

项目可以支撑以下面试讨论：Go 的 `io.Reader` 与固定缓冲区、HTTP 的上传与 Range 下载、PostgreSQL 行级锁、幂等键的范围、校验和、文件系统原子重命名，以及数据库和磁盘不能共同提交的现实限制。

## 二、需求与不变量

文件大小必须为正且不超过配置上限；分片大小有最小和最大值；总分片数不超过 10,000。服务端根据声明的总大小计算每一片的准确长度，尤其是最后一片。客户端不能靠修改 `Content-Length` 绕过实际字节数校验。

每个上传会话有一个服务端随机生成的 32 位小写十六进制 ID。文件名只是展示元数据，不进入磁盘路径。租户由鉴权后端给定；客户端提供的租户字段和任意路径不会决定数据访问范围。

必须保持这些不变量：

- 一条分片元数据对应一个通过长度和哈希校验的磁盘分片。
- 同一上传、同一片号只能提交一种内容；相同内容可重试，不同内容不覆盖。
- 没有全部分片或整体校验失败时不能进入 `COMPLETED`。
- `COMPLETED` 和 `CANCELED` 都是终态。
- 下载只能访问当前鉴权租户已完成的文件。

## 三、架构与职责

```text
客户端 / 演示脚本
        │ X-API-Key + 原始分片字节
        ▼
HTTP API → Upload Service → PostgreSQL（所有者、会话、分片记录）
                  │
                  └────── 本地磁盘（临时文件、分片、完成文件）
```

API 层解析请求并做鉴权、参数和错误映射。Service 层决定状态转换、I/O 顺序与清理。Store 层封装数据库查询和事务。Domain 层保持纯逻辑，如分片数与末片长度计算，便于无需数据库的单元测试。

技术栈采用 Go 1.23 与标准库 HTTP 路由，数据库驱动采用 pgx/v5。没有引入消息队列、Redis 或微服务，避免把注意力从上传协议与一致性问题上移走。

## 四、数据模型

`uploads` 保存 ID、tenant_id、原始文件名、总大小、分片大小、分片数、whole_sha256、状态、创建时间、完成时间。数据库检查约束限制状态与正整数范围。

`upload_chunks` 保存 upload_id、part_number、实际 size、sha256、created_at，主键是 `(upload_id, part_number)`。分片路径由上传 ID、片号和校验和构造，不持有用户输入的路径。

文件布局：

```text
DATA_DIR/
  staging/                    请求接收临时文件
  uploads/<uploadID>/chunks/   <partNumber>-<sha256>.blob
  files/                      <uploadID>.blob 及合并临时文件
```

只有 32 位十六进制 ID、正整数片号、64 位十六进制 SHA-256 能进入内部键。临时文件使用 `os.CreateTemp` 生成随机名称。部署卷必须由服务独占，不能允许不受信任的其他进程植入符号链接；路径约束无法抵御对磁盘本身拥有写权限的攻击者。

## 五、上传分片的顺序

先查询会话和参数，检查片号范围。把请求体流式写入 staging，边写边计算 SHA-256，用 `expectedSize+1` 的读上限检测超量，实际字节不足也拒绝。接收期间不持数据库行锁，降低慢网络占用锁的影响；接收可能继续耗费磁盘直到后续确认会话终态，故仍需要总配额与限并发。

写盘成功后启动事务，用 `SELECT ... FOR UPDATE` 锁住该上传行，再检查状态。如果已经取消或完成，就删除 staging 并返回冲突。如果片号已经存在，哈希与长度相同则视为幂等成功，否则拒绝覆盖。

新分片先重命名到由内容哈希区分的路径，再插入元数据并提交事务。发布临界区中没有网络读取。不同上传不会因为这把行锁相互阻塞，同一上传的发布、合并、取消被串行协调。

并发同片同内容：先完成者提交记录，后完成者读取记录返回成功。并发同片不同内容：先完成者获胜，后完成者返回 409。哈希相同在工程上被当作同内容，仍假设 SHA-256 不发生可利用碰撞。

## 六、完成上传

完成接口持有上传行锁，核对分片数量与每片长度，按片号从 1 到 N 依次读文件。固定大小缓冲区把片段复制到完成目录内的唯一临时文件，同时计算整体 SHA-256；另外重新校验分片自身的 SHA-256，以发现元数据提交后磁盘内容被损坏的情况。

整体长度与声明哈希通过后同步并关闭文件，重命名为 `files/<uploadID>.blob`，更新状态为 `COMPLETED` 并提交数据库。已完成会话重复请求返回同一结果。若数据库提交失败，已发布成品和分片均保留；重试会先校验成品大小及整体 SHA-256，通过后提交完成状态，成品缺失才重建。成功完成后本学习版本也保留分片，因此磁盘占用约为原文件两倍，需要后续清理策略。合并使用数据库行锁，保证写入和取消不能穿插；这是正确性优先的简单方案，代价是大文件合并期间占用一条数据库连接和该会话的锁。请求设置 deadline，客户端可重试。

生产扩展可以引入 `COMPLETING` 状态、合并任务租约、版本号与后台 Worker，缩短长事务。但仅添加状态字段不够，还要设计崩溃恢复、租约过期、重复执行和取消竞争。

## 七、失败与重试边界

数据库和文件系统没有原子事务。以下窗口必须诚实解释：

| 故障点 | 对外状态与处理 |
| --- | --- |
| 接收中断 | 没有分片记录；正常错误退出清理临时文件，进程突然退出可能留下 staging |
| 分片发布后数据库提交失败 | 分片可能变成孤儿；状态接口不会列出，重传可重新发布 |
| 合并校验失败 | 状态仍为 `UPLOADING`；分片不可覆盖，若原始声明或已提交内容错误，取消并重新初始化 |
| 完成文件发布后数据库提交失败或结果未知 | 先查数据库状态；仍在上传时，重试 complete 验证已发布成品的整体大小与哈希后提交状态，成品缺失时根据保留分片重建；不无条件删除成品 |
| 数据库完成提交后响应丢失 | 重试 complete 得到 `COMPLETED`；不用重新上传 |
| 取消提交后磁盘删除失败 | 逻辑取消生效，字节可能残留；重新取消会再次尝试清理 |
| 操作系统突然断电 | `File.Sync` 不能替代目录 fsync 与存储硬件保障；需要恢复扫描与备份方案 |

当前没有自动孤儿扫描或未完成会话 TTL。不要宣传“数据库和磁盘强一致”。部署前应建立保留周期、限额、恢复扫描和管理员可观察的清理任务。清理时必须验证内部 ID，不能按客户端文件名删除文件。

## 八、下载、安全与部署

GET/HEAD 下载由 `http.ServeContent` 处理。它需要可 Seek 的文件，支持 Range 与条件请求；服务端设置由整体 SHA-256 派生的 ETag、下载名和 `application/octet-stream`。HEAD 返回响应头而不传正文，非法 Range 通常得到 416。详见 [Go 官方说明](https://pkg.go.dev/net/http#ServeContent)。

下载时检查完成文件存在、为常规文件且大小匹配，但不为了每个 Range 请求重新扫描整个文件计算 SHA-256。完成后磁盘字节仍应被存储系统保护；若发生同长度的磁盘损坏，客户端需要把完整下载内容再做 SHA-256 与会话声明比较才能发现。ETag 不是自动检查每次读取结果的机制。

固定 API Key 适合本地演示，比较时使用常量时间比较。健康检查不包含凭证。敏感接口不接受查询参数 Key，也不记录请求体或 Key。上传接口有字节、分片数和超时限制，但没有租户累计配额、IP 速率限制、病毒检查或 TLS 终止。

Compose 只暴露 8092，PostgreSQL 不映射宿主机端口；命名卷分别保留元数据与文件。初始化 SQL 只在数据库空卷首次启动时执行，后续迁移需单独管理。当前单副本方案不等于云对象存储；扩展时可参考 [S3 分片上传流程](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)，但不能把 S3 的服务保证直接归于本项目。
