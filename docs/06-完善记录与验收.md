# 分片上传：完善记录与验收

日期：2026-10-04。

## 本轮完善

合法分片的流式读取虽然占内存小，但多个请求仍可能同时占用临时空间、连接与 I/O。因此在鉴权之后、读取/落盘/合并之前添加非阻塞并发门控：

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| MAX_CONCURRENT_UPLOADS | 4 | 每进程同时处理 PUT 分片的上限；允许 1～128 |
| MAX_CONCURRENT_MERGES | 1 | 每进程同时处理 complete 的上限；允许 1～10 |

容量满返回 429，Retry-After: 1；完成或失败后释放容量。状态查询、下载与取消不共享这些槽位。不使用无限等待队列，也不声称这是跨实例全局限流。

新增测试覆盖门控不进入业务、释放容量、Range 206、If-Range 不匹配返回完整文件、HEAD、416 和 ETag 304。下载协议测试直接验证生产使用的 ServeContent 机制，不等于完整“鉴权+数据库查询+磁盘”的端到端测试。

## 仍缺什么

累计租户配额、会话 TTL、孤儿 GC、磁盘剩余空间监控、数据库/磁盘未知提交恢复实验、后台可恢复合并任务。门控限制的是**同时工作数**，不能防止低速长期累积填满磁盘。当前仍推荐单副本、本地卷模型。

## 面试追加题

**有分片上限为什么还需要并发门控？** 单次输入有界不代表 N 个同时输入有界。门控把昂贵的 I/O 和合并同时工作数限定住，且拒绝在读取体之前发生。

**它与限流、配额是什么区别？** 并发控制约束当前在途请求；速率限制约束单位时间请求数；配额约束累计占用。三者互补，本次只新增第一种。

**如何验证跨资源一致性？** 需要真实数据库与磁盘，分别在文件发布后、commit 前后、取消竞争时注入失败，检查可见记录、残留文件和重试结果。纯磁盘单元测试无法证明 SQL 锁顺序。
