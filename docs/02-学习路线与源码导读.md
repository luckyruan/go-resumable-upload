# 学习路线与源码导读

本项目建议投入 7～10 天，目标是独立讲清请求、落盘、下载与失败重试。2026-10-04 单元测试与编译已完成，真实数据库及下面的完整实验仍待执行，见 [完善记录](06-完善记录与验收.md)。

## 第 1 天：明确业务协议

阅读 README 和项目设计。用纸写出 10 字节文件、4 字节分片的划分：第 1 片 4 字节，第 2 片 4 字节，第 3 片 2 字节。再计算 8 字节文件、4 字节分片：只有两片，没有第三片空文件。

理解断点续传不是“服务端记录 TCP 连接断在哪个字节”，而是记录哪些完整分片已经被服务端确认。客户端保留 upload ID 后查询已提交片号；网络中断的半片会重传，不把未确认的临时文件当作成功。

练习：画出 `UPLOADING → COMPLETED`、`UPLOADING → CANCELED` 状态图，列出每个终态允许的接口。解释为什么完成后的 PUT 不能悄悄修改文件。

## 第 2 天：掌握 Go 流式 I/O

阅读 `internal/domain` 的分片计算与错误定义，然后阅读 `internal/service/disk.go`。依次理解 `io.Reader`、`io.LimitReader`、`io.MultiWriter`、`io.CopyBuffer`、`sha256.New`、`os.CreateTemp`、`File.Sync`、`Close`、`Rename`。

关键问题：为什么 `io.LimitReader(body, expectedSize)` 无法区分“恰好大小”与“超过大小”？因为最多只读到 expectedSize；读取 expectedSize+1 才能检测多出的字节。为什么不能对所有请求用 `io.ReadAll`？文件大小会直接变成内存需求，多个并发上传可迅速占满内存。

练习：读懂测试中“短片、超长片、末片、可选分片哈希不匹配”的预期。之后有 Go 环境时可执行测试，再增加“Reader 返回中途错误”的测试。

## 第 3～4 天：理解事务和并发

阅读 `migrations/001_init.sql`，再从 `internal/store/postgres.go` 找到上传行锁和分片唯一键。不要只记住 SQL：要能说明两者各解决什么问题。唯一键限制重复片号；上传行锁统一协调同一会话上的发布、合并与取消。

沿 `internal/service/upload.go` 的 PutPart 走一遍：先 staging，再事务行锁，再状态检查，再幂等判断，再重命名，再插入记录，再 commit。想象两个请求同片同内容、同片不同内容，以及一个 cancel 同时到来的时间线。

练习：回答“如果用进程内 mutex 能不能多副本运行？”进程内锁只覆盖本进程，不能替代数据库协调；即使有数据库锁，多副本独立磁盘也会导致读不到其他副本的分片。

## 第 5 天：理解完成和完整性

阅读 Complete 方法。区分每片哈希、整体哈希与 HTTP ETag。分片哈希用于校验和幂等比较；整体哈希用于确认顺序合并后与原始文件一致；ETag 是 HTTP 验证标识，不天然等于 MD5。项目使用整体 SHA-256 作为 ETag 来源是自己的协议约定。

练习：把两个合法分片顺序调换，整体哈希通常会不同。想一想只把分片哈希字符串再做一次哈希，为什么不能代替原始文件内容的 SHA-256？输入字节完全不同。

## 第 6 天：理解 HTTP API 与下载

阅读 `internal/api/server.go`。找到鉴权中 tenant 的来源；尝试解释为何不能让客户端自由设置 `X-Tenant-ID`。理解 JSON 解析的字节上限、未知字段拒绝、错误码映射、整数片号校验。

阅读 `ServeContent` 调用及 [官方 API 文档](https://pkg.go.dev/net/http#ServeContent)。知道 `Range: bytes=0-99`、`Range: bytes=100-`、`If-Range` 的意义。服务端不必手写 Range 切片解析；使用成熟标准库仍需要正确设置文件、修改时间和响应头。

练习：说明 HTTP 206、416、HEAD 与 ETag 的区别；检查用户文件名为何没有进入文件路径。

## 第 7 天：部署与故障恢复

阅读 Dockerfile、compose.yml、`.env.example`。理解数据库健康检查、app 启动依赖、两个命名卷和默认单副本。初始化 SQL 不等于持续迁移系统，`docker compose down` 不等于删除卷。

阅读项目设计中的故障表，尤其是“文件重命名成功、数据库 commit 失败”。用自己的话写出接口如何重试、残留文件如何产生、后台扫描还需要什么信息。不要把正常请求清理当作突然崩溃恢复。

## 第 8～10 天：完成可用于面试的证据

之后允许运行时，执行接口与手工验证文档中的清单；把实际结果、机器配置与日期保存为新文档。优先验证断点续传、重复提交、缺片完成、整体哈希失败、取消竞争和 Range 下载。压测只能在正确性通过后进行，记录并发数、大小、磁盘、延迟分位数和失败率；没有测量的数据不写进简历。

准备三分钟项目讲解：业务问题 30 秒，上传与恢复流程 60 秒，并发与一致性 60 秒，已验证情况及限制 30 秒。详细问答参考 `04-面试问答与简历.md`。

## 自测题

1. 总大小 1 MiB + 1 字节、分片 1 MiB 时有几片，末片多大？
2. 相同片号为何拒绝不同内容，而不直接覆盖？
3. staging 已写完时上传被取消，如何阻止它“复活”？
4. complete 为什么不能仅依靠分片数判断完整？
5. 同一上传行锁为什么放在网络接收之后？
6. complete 持锁时间变长，下一版如何减少占用而不牺牲恢复能力？
7. 数据库显示完成但磁盘文件丢失，接口应该怎样失败？
8. 两个 Docker 副本用了不同本地卷，数据库行锁能弥补什么、不能弥补什么？
